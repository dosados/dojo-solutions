# BLEU на абзацном уровне (task-1)

Справка для решения задачи **A. Англо-русский переводчик**. Официальное условие: [SPECS.md](SPECS.md).

---

## Что такое BLEU

**BLEU** (Bilingual Evaluation Understudy) — автоматическая метрика качества машинного перевода. Она сравнивает ваш **гипотезу** (перевод модели) с одним или несколькими **эталонными** переводами (reference), которые известны только организаторам на закрытом тесте.

Интуиция: чем больше совпадающих словосочетаний (n-грамм) с эталоном при разумной длине перевода, тем выше балл. BLEU **не** измеряет «красоту» или смысл напрямую, но на корпусах MT обычно коррелирует с человеческой оценкой, если эталоны качественные и стиль согласован.

---

## «На абзацном уровне» в этой задаче

В task-1 один элемент теста — **целый абзац** (в среднем ~846 символов, до ~34 предложений), а не одно короткое предложение.

| Уровень | Что это значит |
|--------|----------------|
| **Единица оценки** | Один `rid` из `input.pickle` = один абзац EN → один абзац RU в `output.json` |
| **Как считают BLEU** | Для **каждого** абзаца отдельно считается BLEU (hypothesis vs reference для этого `rid`) |
| **Итоговый балл** | **Среднее арифметическое** BLEU по всем 69 примерам закрытого теста |

Важно: это **macro-average** (среднее по примерам), а не один общий corpus-BLEU по склеенному тексту всех 69 абзацев. Длинный и короткий абзац влияют на итог **одинаково по весу** (один балл на пример), хотя внутри длинного абзаца n-грамм больше.

Почему организаторы подчёркивают абзацы (см. вступление в SPECS):

- согласованность местоимений и рода по всему тексту;
- единообразие терминов (`fork` / `Fork` → один и тот же вариант в русском);
- связность стиля (прямая речь, цитаты, тон).

Ошибка в середине абзаца бьёт по BLEU так же, как в начале: эталон — на весь фрагмент целиком.

---

## Как устроен BLEU (кратко по формуле)

Классический BLEU (Papineni et al., до вариантов в sacrebleu):

1. **Modified n-gram precision** для n = 1, 2, 3, 4  
   Считается, какая доля n-грамм в вашем переводе встречается в эталоне. Для n > 1 берётся **максимум** по нескольким эталонам, если их несколько (в контесте обычно один reference на пример).

2. **Brevity penalty (штраф за краткость)**  
   Если перевод **короче** эталона, балл режется. Слишком короткий ответ («сжали» абзац) сильно просаживает BLEU даже при точных словах.

3. **Геометрическое среднее** по четырём порядкам n-грамм  
   Обычно с весами ¼ на каждый n; нулевая precision на каком-то n сильно тянет вниз.

4. **Шкала**  
   В отчётах sacrebleu score часто в диапазоне **0–100** (проценты), не 0–1. Сравнивайте числа в одной системе (sacrebleu vs другая библиотека).

Что метрика **любит**:

- те же слова и фразы, что в reference (включая устойчивые формулировки);
- похожую длину текста;
- совпадение имён, чисел, пунктуации, если они есть в эталоне.

Что **наказывает**:

- лишний текст (см. ниже про преамбулы);
- пропуски целых фраз;
- систематически другой выбор синонима, если в эталоне зафиксирован один вариант;
- сильное отклонение по длине.

Два перевода могут быть **смыслово верными**, но получить разный BLEU — если эталон один и формулировка другая.

## SacreBLEU в контесте

В условии указано: метрика считается через библиотеку **[sacrebleu](https://github.com/mjpost/sacrebleu)**.

SacreBLEU фиксирует детали, которые в старых статьях плавали:

- токенизацию (для разных языков свои правила);
- версию BLEU (часто близко к **BLEU + cumulative brevity penalty**, как в Moses/multi-BLEU);
- нормализацию пробелов и знаков.

Для локальной отладки разумно использовать **ту же** библиотеку и по возможности те же настройки, что на сервере. Точный конфиг токенизатора для пары EN→RU на закрытом тесте организаторы не публикуют; на практике для русского гипотезы часто используют стандартный вызов `sacrebleu` без экзотики — но **локальный BLEU на своём dev-наборе** всё равно только ориентир, пока нет тех же reference, что на контесте.

### Агрегация как на контесте (macro-average)

Псевдокод, соответствующий описанию в SPECS:

```python
import sacrebleu

hypotheses = [...]   # список переводов, порядок = порядок rid
references = [...]   # список эталонов той же длины (на dev-данных)

per_example = []
for hyp, ref in zip(hypotheses, references):
    # один reference на пример: список из одной строки
    score = sacrebleu.sentence_bleu(hyp, [ref])
    per_example.append(score.score)

final_score = sum(per_example) / len(per_example)
```

Не путать с `corpus_bleu(hypotheses, [references])`: corpus-версия **взвешивает** длинные тексты сильнее и **не** равна среднему sentence_bleu в общем случае.

Установка в **ml-env**:

```bash
conda run -n ml-env pip install sacrebleu
```

## Что особенно важно для EN→RU и этой задачи

### 1. Только перевод в `translation`

Организаторы прямо предупреждают: фразы вроде *«Вот перевод с английского на русский»* **снижают** BLEU — это лишние n-граммы, которых нет в эталоне. В бейзлайне в `solution.py` промпт как раз отсекает комментарии:

```19:24:task-1/submission/solution.py
GENERAL_PROMPT = """
Ты профессиональный переводчик. Твоя задача перевести текст с английского на русский.
ВАЖНО чтобы в ответе был только перевод без каких-либо комментариев и уточнений.

Текст для перевода:
"""
```

Проверяйте постобработкой: обрезка markdown, кавычек, префиксов ассистента, повторения исходного EN.

### 2. Один абзац — один непрерывный перевод

Не разбивайте вывод на нумерованные списки «по предложениям», если эталон — сплошной текст. Не вставляйте заголовки `Перевод:` / `Translation:`.

### 3. Согласованность внутри абзаца

Типичные промахи из условия задачи (плохо и для смысла, и для BLEU, если эталон согласован):

| Проблема | Пример |
|----------|--------|
| Местоимения / род | *Danius said … when **she*** → неверное «когда **она**» |
| Термины | *fork* / *Fork* → везде один вариант (*форк*, не «вилка» в кнопке) |
| Прямая речь | искажение структуры цитаты относительно эталона |

Промпты в духе «сохраняй терминологию», few-shot с согласованным абзацем, или постредактура по глоссарию часто дают прирост именно на длинных `src`.

### 4. Длина и полнота

Для длинных абзацев (до ~400 слов) следите за `max_new_tokens` и обрезкой: незаконченный хвост абзаца = пропущенные n-граммы + brevity penalty.

### 5. Синонимы и «красивый» русский

Человеку перевод с синонимом может нравиться больше; BLEU с одним reference — нет. На dev-наборе смотрите, не уходит ли модель в стилистику, которая стабильно ниже вашего эталона.

### 6. Знаки, числа, имена

Лишние/пропущенные кавычки, дефисы, пробелы перед `%` дают расхождение по 1–4-граммам. Имеет смысл нормализовать только то, что не меняет слова (пробелы), и не «исправлять» имена без необходимости.

## Локальная оценка без закрытого теста

На **contest.yandex.ru** reference для 69 тестовых `rid` не отдают. Поэтому:

| Что можно | Что нельзя |
|-----------|------------|
| BLEU на своём parallel dev (WMT, Opus, выборка с ручным эталоном) | Точно воспроизвести балл контеста до отправки |
| Сравнивать варианты промпта/модели между собой на одном dev | Гарантировать тот же rank, что на скрытом тесте |
| Смотреть примеры глазами + chrF/TER (дополнительно) | Подгонять только под один dev и забыть про обобщение |

Рекомендуемый цикл:

1. Прогон `examples/example-input.pickle` — smoke test формата и скорости Docker (сборка из `submission/`).
2. Dev-корпус EN–RU с эталонами → macro-average BLEU как выше.
3. Ручной разбор 5–10 абзацев с низким sentence BLEU: обрезка, мусор в начале, термины, местоимения.
4. Отправка zip на контест (4 попытки / 24 ч) — единственный «истинный» скор.

Пример минимального скрипта оценки (файлы `dev.hyp.txt` и `dev.ref.txt`, по одной строке на абзац, экранирование переносов — отдельная тема):

```python
import sacrebleu

hyps = open("dev.hyp.txt", encoding="utf-8").read().splitlines()
refs = open("dev.ref.txt", encoding="utf-8").read().splitlines()
assert len(hyps) == len(refs)

scores = [sacrebleu.sentence_bleu(h, [r]).score for h, r in zip(hyps, refs)]
print(f"macro BLEU: {sum(scores) / len(scores):.2f}")
print(f"min / max: {min(scores):.2f} / {max(scores):.2f}")
```

## BLEU и качество: ограничения метрики

Имеет смысл помнить, чтобы не оптимизировать «в ноль» не то:

- **Один эталон** — другая допустимая формулировка проигрывает.
- **Поверхностное совпадение** — калька с EN может набрать BLEU выше идиоматичного русского, если эталон калькован.
- **macro-average** — один провальный абзац из 69 так же важен, как один отличный; нет «спасения» за счёт длины соседей.
- **Закрытый тест** — переобучение на публичные leaderboard-утечки недопустимо и бессмысленно; опирайтесь на свой dev и здравый смысл.

Для task-1 цель организаторов совпадает с хорошим переводом абзаца: связный, полный, без мусора в выводе, с устойчивой терминологией — это обычно и поднимает BLEU на их эталонах.
