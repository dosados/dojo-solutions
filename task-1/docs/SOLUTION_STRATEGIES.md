# Стратегии решения task-1 (EN→RU, абзацы)

Справочник по вариантам улучшения бейзлайна **google/gemma-4-E2B-it**. Официальное условие: [SPECS.md](SPECS.md). Метрика: [BLEU.md](BLEU.md).

**Цель документа:** собрать контекст задачи, ограничения контеста, выводы из литературы (2024–2026) и упорядоченный каталог подходов — от «лёгких» до ресурсоёмких — с указанием инструментов, **объёма данных** и влияния на папку `weights/`.

**План по фазам:** [IMPLEMENTATION_ROADMAP.md](IMPLEMENTATION_ROADMAP.md).

---

## 1. Суть задачи

| Параметр | Значение |
|----------|----------|
| Направление | Английский абзац → русский абзац |
| Тест | 69 примеров, ~846 символов в среднем, до ~2229 символов |
| Модель (рекомендация организаторов) | `google/gemma-4-E2B-it` (~2.3B effective, IT) |
| Метрика | **Macro-average BLEU** (sacrebleu `sentence_bleu` по каждому `rid`, затем среднее) |
| Обучающие данные от организаторов | Нет (но finetune на публичных корпусах разрешён) |

Организаторы явно выделяют **абзацный** перевод, а не предложения:

- согласованность местоимений и рода;
- единообразие терминов внутри текста;
- сохранение структуры цитат и стиля.

Бейзлайн (`solution.py`) — zero-shot IT-модель с простым промптом, batch size 1, `max_new_tokens=1024`.

## 2. Ограничения контеста (жёсткие рамки)

| Ограничение | Значение | Следствие для дизайна |
|-------------|----------|------------------------|
| Сеть в рантайме | **Нет** | Все веса, адаптеры, глоссарии, зависимости — в zip / Docker image |
| Время | **≤ 45 мин** на 69 запросов (~39 с/абзац в среднем) | Нужен быстрый инференс; тяжёлые ensemble/MBR — только если влезают |

## 3. Целевая метрика: что оптимизировать

### 3.1 Macro-average BLEU (sacrebleu)

- Один провалившийся абзац из 69 **равен по весу** удачному (не corpus-BLEU).
- Оптимизация «среднего по dev» ≠ гарантия на закрытом тесте, но **ранжирование** вариантов на одном dev-корпусе полезно.

### 3.2 Что BLEU поощряет / наказывает

| Плюс для BLEU | Минус для BLEU |
|---------------|----------------|
| Совпадение n-грамм с reference | Преамбулы («Вот перевод…») |
| Похожая длина перевода | Сильная краткость (brevity penalty) |
| Те же имена, числа, кавычки | Синонимы, если в эталоне другая формулировка |
| Стабильный термин по всему абзацу | Обрыв генерации на `max_new_tokens` |

**Практический вывод:** для контеста важны **чистый вывод**, **полнота абзаца**, **согласованная лексика** — это совпадает с качественным переводом и обычно поднимает BLEU на типичных news/wiki эталонах.

### 3.3 Локальная оценка (без закрытого теста)

| Набор | Назначение | Ограничение |
|-------|------------|-------------|
| `examples/example-input.pickle` | Smoke: формат, Docker, время | Нет reference |
| **FLORES-200** `dev` / `devtest` (`eng_Latn` ↔ `rus_Cyrl`) | ~997 / ~1012 **предложений** | Длина ~21 слово — не абзацы; только ориентир |
| **OPUS** (Wiki, News, TED, …) EN–RU | Много параллельного текста для SFT/LoRA | Нужна фильтрация и, для dev, **склейка в абзацы** или отдельный paragraph dev |
| WMT / UN parallel / ParaCrawl (с фильтром) | Доп. данные для обучения | Качество разное |

Рекомендуемый скрипт агрегации — macro-average, как в [BLEU.md](BLEU.md). Дополнительно: **chrF++**, **COMET** — для анализа, но финальный скор только BLEU.

## 4. Модель и контекст (Gemma 4 E2B)

**Gemma 4** (Google DeepMind, 2026): семейство открытых мультимодальных моделей, **140+ языков**, контекст **128K** (E2B/E4B). E2B — edge-вариант (~2.3B effective), в задаче — **instruction-tuned** `gemma-4-E2B-it`.

Для MT релевантно:

- сильная мультиязычность из pretrain + IT;
- chat template и `parse_response` в transformers (как в бейзлайне);
- `enable_thinking=False` — отключение режима рассуждений (экономия токенов и времени).

**Ограничение размера:** E2B — «маленькая» модель для абзацев; прирост часто идёт от **промпта, данных, document-level приёмов**, а не от смены на 31B (не влезет в лимиты без квантизации и риска по времени).

## 5. Исследования: document-level MT и LLM (2024–2026)

Краткая выжимка релевантных направлений (без привязки к конкретной реализации в репо).

| Направление | Идея | Релевантность для task-1 |
|-------------|------|-------------------------|
| **DocMT-LLM + DOCBLOCKS** (arXiv:2504.12140) | SFT на document-level парах; long-range coherence | LoRA/SFT на **абзацных** парах EN–RU |
| **DELTA** (arXiv:2410.08143) | Агент с multi-level memory (имена, краткое содержание) | Термины и местоимения в длинных `src` |
| **SubDocTrans** (EMNLP 2025 Findings) | Сегментация на sub-doc + извлечение знаний в промпт | Согласованность без полного дообучения |
| **Contextual APE** (NAACL 2024) | LLM постредактирует черновик с контекстом | Второй проход / тот же LLM |
| **LoRA best practices** (PEFT, WMT’24 отчёты) | LoRA на MLP+attention, LR ~10× выше FFT, α ≈ 2r | QLoRA на L4 при обучении |
| **Prompt / P-tuning** (PEFT, DePT arXiv:2310.10094) | Обучаемые soft prompts, низкий rank | Мало параметров; риск слабее LoRA на MT |

**Общий вывод литературы:** sentence-level LLM-MT уже сильны; **абзацы** требуют явного контекста (prompt, memory, doc-SFT) или **двухпроходных** схем. Для Gemma 2B разумный баланс — **промпт + лёгкий LoRA**, а не тяжёлый agent на 69 примерах.

## 6. Объём данных: как читать оценки

В задаче **нет** размеченного train от организаторов. Ниже — сколько **своих** данных нужно, чтобы подход был **корректно внедрён** (не «запустился», а дал стабильный сигнал на dev и не переобучился).

### 6.0. Единицы и роли наборов

| Единица | Ориентир для task-1 | Где взять |
|---------|---------------------|-----------|
| **Предложение** | ~20 слов (FLORES) | OPUS, WMT, FLORES |
| **Псевдо-абзац** | 3–8 предложений, ~150–600 слов | Склейка соседних предложений одной статьи OPUS/Wiki |
| **Абзац (как в тесте)** | ~162 слова, до ~401 слова | Склейка по URL/документу или WMT document-level |

| Роль набора | Зачем | Минимум | Комфортно |
|-------------|-------|---------|-----------|
| **Smoke** | Формат, Docker, время | `examples/example-input.pickle` (без ref) | + 10–20 ручных пар EN–RU |
| **Dev (оценка)** | Macro BLEU, выбор промпта/модели | 100 псевдо-абзацев с эталоном | 300–500 абзацев |
| **Train (обучение)** | LoRA / SFT / prompt tuning | Зависит от уровня (см. ниже) | — |
| **Контест** | 69 скрытых `rid` | Только инференс | 4 попытки / 24 ч |

**Важно:** FLORES-200 `dev` (~997 предложений) — хороший **sentence-level** dev, но **не заменяет** абзачный dev: для промпта и LoRA под длинные тексты соберите отдельный **paragraph-dev** (склейка или WMT/news документы).

## 7. Варианты решения (по возрастанию сложности)

Оценки **сложности реализации** и **«тяжести»** (время разработки, риск уложиться в 45 мин / 20 GB) — субъективные, для планирования.

Легенда:

- **Сложность:** ★ (низкая) … ★★★★★ (высокая)
- **Тяжесть:** 🪶 лёгкая … 🪨 тяжёлая (образ, время, отладка)
- **Ожидаемый эффект на BLEU:** + (низкий) … +++ (высокий, при удачном dev)
- **Данные:** минимум для корректного внедрения → рекомендуемый объём

### Уровень 6 — LoRA / QLoRA (рекомендуемый путь к finetune)

| | |
|--|--|
| **Что** | SFT на парах EN–RU (желательно **абзацы** или склеенные 3–5 предложения); LoRA на `q_proj,k_proj,v_proj,o_proj` + **MLP** (`gate, up, down`); rank 8–64; LR ~1e-4 … 2e-4; 1–3 эпохи на отфильтрованном подмножестве |
| **Сложность / тяжесть** | ★★★★ / 🪨 (обучение) + 🪶 (инференс с merge) |
| **Эффект** | ++ … +++ |
| **Файлы (локально)** | `train_lora.py`, `configs/lora.yaml`, `merge_lora.py` |
| **Файлы (контест)** | `solution.py` / `inference.py` |

**`weights/` — два варианта:**

| Вариант | Структура | Плюсы / минусы |
|---------|-----------|----------------|
| **A. Адаптер в zip** | `weights/` база + `weights/lora/` (`adapter_config.json`, `adapter_model.safetensors`) | Мало пересборок; нужен `peft` в Dockerfile |
| **B. Merge перед сдачей** | Заменить `model.safetensors` | Проще `solution.py`; долгая пересборка zip |

**Инструменты:** `peft`, `trl` (SFTTrainer), `bitsandbytes` (QLoRA 4bit при обучении), `datasets`, **Unsloth** / **LLaMA-Factory** (опционально), **OPUS** ([opus.nlpl.eu](https://opus.nlpl.eu/)), Hugging Face `Helsinki-NLP/opus-*`.

**Данные (примеры):**

| Источник | Тип | Замечание |
|----------|-----|-----------|
| OPUS Wiki/News/TED EN–RU | Параллельные предложения | Склеить в pseudo-paragraphs или фильтровать длинные сегменты |
| WMT news EN–RU | Качественные новости | Хорошо для стиля теста |
| FLORES-200 devtest | Оценка | Не для обучения на test; dev для валидации |
| Синтетика | Back-translation RU→EN | Риск шума; осторожно с BLEU-overfit |

**Данные (объём для корректного LoRA):**

| Режим | Train | Valid (hold-out) | Комментарий |
|-------|-------|------------------|-------------|
| **Пилот** (проверка пайплайна) | **3k–10k** предложений EN–RU | 500 предложений | Быстро; прирост BLEU может быть шумом |
| **Минимум осмысленный** | **20k–50k** предложений **или** **2k–5k** псевдо-абзацев | 1k предл. / 200–500 абзацев | Уже виден тренд на paragraph-dev |
| **Рекомендуемый** | **100k–300k** отфильтрованных предложений **или** **10k–30k** абзацев (150–400 слов) | 2k–5k предл. / 300–800 абзацев | Баланс качество/время на 2B + QLoRA |
| **Агрессивный** | **500k–1.5M** предложений | 5k–10k предл. | Риск домена news/wiki; нужна фильтрация длины и языка |
| **Doc-style (как в литературе)** | **5k–50k** document blocks (~200–800 токенов) | 500–2k blocks | Ближе к тесту; дороже собирать |

**Правила:**

- Формат обучения = тот же chat template и инструкция, что в `solution.py`.
- **Не смешивать** valid с train; FLORES `dev` — ok для valid, **не** train на `devtest` перед контестом.
- После **>300k** предложений на E2B часто плато; лучше чистота и абзацная структура, чем сырой ParaCrawl.

**Риски:** переобучение на news-стиль; забыть `enable_thinking=False`; забыть тот же chat template при обучении.

---

### Уровень 7 — Prompt tuning / P-tuning / Prefix tuning

| | |
|--|--|
| **Что** | Обучаемые virtual tokens (PEFT: `PromptTuningConfig`, `PrefixTuningConfig`, `PromptEncoderConfig`) при замороженной базе |
| **Сложность / тяжесть** | ★★★★ / 🪶 (размер) + ★★★★ (подбор) |
| **Эффект** | + … ++ (для MT часто **слабее LoRA** на генеративных задачах) |
| **`weights/`** | `weights/soft_prompt/` или файлы в `weights/` + загрузка через PEFT |
| **Данные** | **Train: 1k–5k** (минимум, часто нестабильно на MT) → **10k–50k** пар предложений или **1k–5k** абзацев. **Valid: 200–1000** примеров. **Virtual tokens:** 20–100 (подбирать под длину инструкции). Меньше параметров, чем LoRA, но на генеративном MT обычно нужен объём **не меньше 5k** качественных пар, иначе high variance на macro BLEU. |

**Инструменты:** `peft` ([soft prompts guide](https://huggingface.co/docs/peft/en/conceptual_guides/prompting)).

**Когда имеет смысл:** очень мало VRAM на обучение, нужно несколько «голов» (редко для одной задачи контеста).

---

### Уровень 8 — Полный supervised fine-tuning (FFT)

| | |
|--|--|
| **Что** | Обновление всех весов (или большого слоя) на большом EN–RU корпусе |
| **Сложность / тяжесть** | ★★★★★ / 🪨🪨 |
| **Эффект** | +++ при достаточных данных и вычислениях; риск catastrophic forgetting |
| **`weights/`** | **Полная замена** чекпоинта (новый `model.safetensors`, сохранить tokenizer + chat template) |
| **Данные** | **Минимум не рекомендуется:** < **50k** пар — высокий риск забывания IT-способностей Gemma. **Практический минимум:** **100k–300k** предложений. **Рабочий диапазон:** **500k–2M+** отфильтрованных EN–RU. **Valid:** 5k–10k. **Абзачный FFT:** **10k–100k** абзацев (если есть). На 2B полный FT без сотен тысяч примеров редко оправдан vs LoRA. |

**Инструменты:** `trl`, DeepSpeed, multi-GPU локально (не на L4 контеста).

**Ограничение 20 GB:** один полный E2B ~10 GB — ок; дубликат базы + FT — нет.

---

### Уровень 9 — Постредактура вторым проходом / вторая модель

| | |
|--|--|
| **Что** | Pass 1: перевод; Pass 2: «исправь только термины и согласование, не меняй стиль»; или маленькая модель-редактор |
| **Сложность / тяжесть** | ★★★★ / 🪨🪨 (2× latency) |
| **Эффект** | ++ при укладывании во время |
| **`weights/`** | Одна модель — без изменений; две — `weights/` + `weights_editor/` (жёстко по 20 GB) |
| **Данные** | **Zero-shot 2-pass (промпт): train 0**, dev **100–200** абзацев — убедиться, что второй проход не портит BLEU. **LoRA-APE:** **10k–100k** троек (src, черновик MT, исправленный ref) или синтетика «черновик = baseline, ref = OPUS». **Время:** 2×69 инференсов — отдельный бенчмарк без ref. |

**Литература:** NAACL 2024 contextual refinement / APE.

---

### Уровень 10 — Reranking / MBR / ensemble

| | |
|--|--|
| **Что** | N гипотез с разным seed/prompt → выбор по proxy-BLEU (нужен dev ref) или COMET; Minimum Bayes Risk decoding |
| **Сложность / тяжесть** | ★★★★★ / 🪨🪨🪨 |
| **Эффект** | ++ на dev, часто **не влезает** в 45 мин без ускорения |
| **`weights/`** | Одна модель |
| **Данные** | **Train: 0** (MBR / best-of-N по BLEU на dev). **Dev с reference: 300–1000** абзацев — стабильный выбор гипотезы; **100–200** — только грубый тренд. **N гипотез:** 2–5 на пример → **×N** время инференса. Обучаемый reranker (опционально): **20k–100k** пар (src, hyp, score). |

**Инструменты:** `sacrebleu`, `unbabel-comet` (только локально для выбора).

**Для контеста:** только если N=2–3 и быстрый инференс (уровень 4).
